# Glass Markdown Note Context

## Current Direction

Build LumaNote, a native macOS SwiftUI sticky note app focused on one compact frosted-glass note that can stay at the edge of the screen.

The selected visual direction is a fusion of the generated `Bottom Rail Note` and `Slim Strip Note` concepts:

- One resizable frosted-glass note, not a dashboard.
- Content area takes priority.
- A slim bottom rail holds the main controls.
- The opacity slider runs from 0% to 100%.
- The bottom rail includes a compact file switcher for recent Markdown/text files plus Save As for the current note.
- Extra controls stay behind compact icon buttons or popovers.
- Clipboard suggestions appear as a compact top-bar island/popover, not a large permanent panel.

## Required Product Behavior

- Markdown note editing with live save.
- Markdown should render live inside the editable note body, not through separate edit/preview modes.
- First launch should open a real example Markdown document that demonstrates common Markdown syntax and clickable task items.
- Adjustable note opacity. New default note opacity is 60%.
- Adjustable theme color for the app's accent tone.
- Customizable global shortcuts for toggling the note, showing the note, hiding the note, and opening the clipboard library.
- App-level Chinese/English UI language switch in Settings. This changes app chrome text, not the user's Markdown content.
- App-level appearance mode in Settings and the compact More panel: follow system, force light, or force dark. The default is system.
- Clipboard history saved locally after explicit app setting enables monitoring.
- Clipboard detection suggestions for URL, email, phone, address-like text, macOS local file paths, labeled codes such as verification codes or order/tracking numbers, and labeled free text after a colon.
- Polished SwiftUI/macOS visual style with frosted glass and subtle slide/fade behavior.

## Implementation Notes

- The note opacity slider controls the glass/readability layers, not the whole NSWindow alpha. Text and controls intentionally stay readable.
- `AppSettings` is the source of truth for persisted slider ranges. Note opacity is normalized to 1%-100%, glass texture strength to 0%-100%, editor font size to 11-28 pt, and `NaN` values fall back to defaults before they can reach `NoteGlassMetrics` or Markdown styling; keep Settings, More, and bottom rail sliders on these shared constants.
- Main note glass formulae for material opacity, white haze, accent tint, border opacity, island opacity, bottom rail opacity, and collapsed chrome opacity live in `NoteGlassMetrics.swift`; keep slider math there instead of scattering it through `NoteWindowView`. `NoteGlassMetrics` also normalizes direct inputs so `NaN`, infinity, out-of-range values, or a bad minimum opacity cannot leak into `pow(...)` or bottom-rail division; this is a defensive boundary and should not change valid slider values.
- The compact settings copy distinguishes shell visibility from glass texture: shell visibility controls the main shell and a reduced white haze contribution, while glass texture mostly controls highlights, edges, subtle refraction, and only a small added material thickness. Avoid letting the glass texture slider make the note read as a pure white sticky note. Current main-shell ranges: note opacity slider input 1%-100%, glass texture slider input 0%-100%, shell material opacity about 8%-69%, white haze about 0.6%-19.1%, theme tint/refraction about 0.5%-8.5%, and shell border about 18%-98%; the top-end material/haze/tint values include a 15% opacity-endpoint boost that ramps in with the shell visibility curve. New-user defaults are note opacity 60% and glass texture strength 20%. The 2026-06-15 semantic split experiment was rejected visually; keep this closer-to-original formula unless the user asks for a new direction.
- In-window floating panels are mutually exclusive. Opening the clipboard library, file switcher, more/settings panel, shortcut settings sheet, or top clipboard extraction actions should close or replace the other floating panels; clicking outside an inline panel or leaving the note window should close any inline transient panel. `NoteWindowOverlayController` owns the single `NoteWindowTransientOverlay?` state and the tested toggle/close/sheet helpers, so new panels should extend that enum and controller instead of adding another independent `show...` flag to `NoteWindowView`.
- The compact more menu and file switcher overlay sizing, anchor fallback, edge clamping, coordinate-space name, and button-frame preference keys live in `NoteWindowOverlayLayout.swift`. Keep overlay geometry there instead of adding more placement math to `NoteWindowView`. Tiny-window edge cases are covered by layout tests: when the panel is wider or taller than the available note area, the clamped center should fall back to the available midpoint instead of hugging a clipped edge.
- Settings and the compact More menu include a Markdown editor font-size slider. It persists under `editorFontSize`, defaults to 15.5 pt, clamps to 11-28 pt, and the live Markdown styler scales headings, inline code, code blocks, lists, and task checkboxes from that body size.
- Markdown editing uses `MarkdownRenderingEditor.swift`, an editable `NSTextView` that live-styles the Markdown source. It saves plain Markdown.
- Markdown syntax detection rules and pure parsing helpers live in `MarkdownStyleRules.swift`; style attribute recipes such as fonts, colors, paragraph spacing, code fence and hidden syntax attributes live in `MarkdownStyleAttributes.swift`. Keep regex/rule additions and visual text-style tuning in those files instead of growing `MarkdownRenderingEditor.Coordinator`.
- When the editor has IME marked text, such as Chinese input method candidates or English candidate words typed through a Chinese input method, do not run Markdown restyling, do not reset the attributed string, and do not write the temporary marked text back to the bound note body. Wait until `hasMarkedText()` becomes false, then save and re-style. Resetting attributes while marked text is active can corrupt the input method composition and produce garbled candidate text.
- Markdown compatibility notes for GitHub are documented in `docs/markdown-compatibility.md`. The app saves original Markdown text, but the live editor is a lightweight visual styler rather than a full CommonMark/GFM renderer.
- Recent Markdown styling additions include underscore italic, bold italic, tilde fenced code blocks, nested quote/list indentation, GitHub Alert headers, email/autolink styling, reference/wiki link styling, image-reference styling, highlight syntax, and emoji shortcode token styling.
- Link and code styling now avoid cross-contamination: Markdown links accept common destination forms with one level of parentheses or angle-bracket destinations, and fenced code blocks / inline code spans are excluded from later inline Markdown scans so URLs or link-like text inside code stay code-styled.
- Inline Markdown markers for bold, italic, bold italic, strikethrough, highlight, inline code, Markdown links, image syntax, wiki links, and autolinks are now visually hidden through a TextKit hidden-syntax attribute plus `NSLayoutManager.GlyphProperty.null`. Do not replace this with only transparent foreground color, because that still leaves ugly marker spacing. Fenced code blocks are tracked as block items and drawn by `MarkdownTaskTextView` as rounded code panels with a language title and a copy button, while the saved source text keeps the original fences. The code-block copy button feedback uses a cancellable delayed selector with a 1.15s duration; cancel the pending reset when code blocks refresh or another copy occurs instead of queuing raw delayed closures.
- Hidden Markdown syntax is intentionally local-editable: when the selection/caret enters a styled inline element or fenced code block, that element's source syntax is temporarily revealed so the user can edit `**` markers, link destinations, inline-code backticks, or code fence language text in place. When the caret leaves, the syntax collapses back to the cleaner rendered display. Avoid turning this into a global edit/preview mode switch unless the user explicitly changes the product direction.
- Heading markers such as `# ` are also hidden by the same TextKit zero-width syntax path, while H1-H3 draw a very faint separator line under the heading. The reveal hit zone for inline Markdown should include the element boundary, not only the middle of the visible text, so clicking just beside a short link/image label can still expose the original Markdown. Code fence lines are different from inline syntax: keep them transparent but layout-preserving in the collapsed state rather than zero-width hidden, so collapsed and active code blocks have the same vertical spacing. Code block opening fences use a compact 3 pt paragraph spacing before the panel plus small panel padding; keep the divider near the language row rather than touching code text. Closed code block ranges should stop at the closing fence characters, not the newline after them, and the drawn code panel should be centered inside the text container instead of borrowing asymmetric outer bounds. The rendered code panel must include the closing fence line, even when the three backticks are transparent, so the panel does not look clipped; it should still exclude any newline or blank line after the closing fence. When drawing the panel, use an exact glyph range from the first opening-fence character to the last closing-fence character and filter line fragments whose character range starts after the block end; `glyphRange(forCharacterRange:)` can pull in the blank line after the closing fence and make the panel grow when the user presses Return after the three backticks. The panel bottom padding is -2 px because the hidden closing-fence line already contributes its own line height and 1.5 pt line spacing; the closing fence paragraph spacing is 11 pt to give the following text breathing room without letting the panel overlap it.
- The Markdown editor's enclosing `MarkdownScrollView` disables AppKit's built-in vertical scroller and draws its own slim right-edge scroll indicator as an overlay subview. Do not return to subclassing `NSScroller` for this surface; AppKit can still hide or skip drawing it in overlay mode. The custom overlay draws only the floating thumb, not a separate track. It stays visible as a thin idle thumb whenever the content is scrollable, briefly becomes clearer and wider while scrolling or while the pointer is over it, then animates back to a visible low-opacity idle state after about 1 second. The scroll indicator uses cancellable idle/animation tasks and clears completed task references so repeated scroll/hover cycles do not retain stale tasks. Scroll progress is calculated from the text layout manager's actual used height plus the document visible rect, with a re-entrancy guard around layout refreshes. During live window resize, `MarkdownScrollView` reuses the cached document height and defers both exact TextKit height measurement and document-frame width/height updates until resize ends; changing the document frame during every resize tick forces TextKit reflow and makes corner dragging stutter. The editor uses a `MarkdownDocumentView` as the scroll document: the `NSTextView` is sized to the real text layout height, while the document container adds bottom breathing space equal to about two thirds of the visible editor height. This keeps the current typing line nearer the middle of the note when scrolled to the bottom without inflating the text view itself, so TextKit's own insertion-point scrolling no longer fights an artificial text-view height. Do not reintroduce delayed keyDown/textDidChange scroll anchoring for this behavior; styling selection-restore may still suppress auto-scroll locally because Markdown restyling should not move the viewport. The note body outer padding is biased left by about 10 px to visually balance the right-side scroll indicator.
- Markdown styling now avoids the duplicate full-document pass from SwiftUI `updateNSView` after user edits. Markdown regexes are cached as static rules, `MarkdownStyleAttributes` caches same-font style fonts for a pass, task/list prefix styling reuses per-pass `MarkdownTaskLayoutMetrics` for same-font measurements, and the custom scroll indicator caches document height until text/layout width changes, so ordinary scrolling no longer repeatedly forces full text layout measurement.
- `NoteStore.swift` owns current-note state, save/open tasks, deferred startup file loading, active workspace selection, and preview-cache invalidation. Pure workspace/defaults helpers such as recent-file loading, workspace normalization, default workspace creation, and defaults keys live in `NoteWorkspaceSupport.swift`; title extraction and the first-launch example document live in `NoteDocumentMetadata.swift`. Keep helper/template changes out of `NoteStore`. Save/open tasks use generation guards and cancellable helper paths so a stale save/open task cannot clear or update state after a newer task has replaced it; tests cover task-reference cleanup after completion. During deferred startup loading, the empty placeholder must not be written back to the previous note if the user saves, switches files, creates a new Markdown file, or quits before the real file content arrives; the initial-load task is tracked/cancellable separately from normal open/save tasks.
- `- [ ]` and `- [x]` are rendered as clickable checkboxes while keeping the underlying Markdown text.
- Task markers should not use a tiny hidden font because that makes the insertion caret short near a task marker. The current implementation parses each task line into indentation width plus a fixed checkbox slot, then dynamically computes the hidden marker kern so `- [ ]`, `- [ ] `, `- [ ]  `, `- [x] `, and newly typed tasks occupy the same visual slot.
- Checkbox drawing should use `lineFragmentRect.minX + textContainer.lineFragmentPadding + parsed indentation width`, not marker trailing position or ad hoc constants. The `lineFragmentPadding` term matters because ordinary text starts after AppKit's text-container padding; omitting it makes checkbox left edges fail to align with non-task paragraph text.
- `MarkdownTaskTextView.insertNewline(_:)` handles task continuation. Pressing Return on a non-empty `- [ ]` or `- [x]` line inserts a new `- [ ]`; pressing Return on an empty task line exits the task list by deleting only the current line's task marker/content range, not by inserting or replacing with another newline.
- The Markdown editor disables `NSTextView` automatic text completion, text checking, link/data detection, spelling correction, smart insert/delete, quote substitution, dash substitution, and text replacement. Keep these off so macOS does not auto-continue a plain hyphen list after the app has exited an empty task item.
- The opacity slider now bottoms out at 1%, not 0%. The lowest state keeps a faint glass silhouette, border, and visible control rail so the note does not degrade into frameless floating text.
- The top empty drag area shows three narrower, thinner semi-transparent horizontal bars so users know they can drag there.
- The visible bars stay small, but the invisible `WindowDragView` now fills the full top drag strip and the bars ignore hit testing, so dragging directly on the visible bars should always hit the AppKit drag layer.
- `WindowDragView.swift` overrides `acceptsFirstMouse` so the drag strip can receive the first mouse/trackpad event even while QuietNote is inactive. This is intended to make three-finger dragging work without first focusing the app.
- The top island must not be implemented as a normal SwiftUI `Button`; it blocks three-finger dragging. Use `WindowClickDragView` for the island hit target so short clicks open clipboard/actions and drag gestures call `window.performDrag`.
- The app stores data locally under `~/Library/Application Support/QuietNote/`.
